# 05 · 观测与排障手册

> 对应用例：`obs-01` ~ `obs-09`
> 核心思想：**没有观测的并发代码，等于在黑暗中开车。**

---

## 1. 必须采集的指标

### JVM 层

| 指标 | 来源 | 告警建议 |
|---|---|---|
| 堆使用率 | `MemoryMXBean` / `jstat` | > 85% 持续 5 分钟 |
| GC 次数与耗时 | `GarbageCollectorMXBean` | GC 时间占比 > 10% |
| 线程总数 / 峰值 | `ThreadMXBean` | 持续增长或 > 500 |
| CPU（进程/系统） | `OperatingSystemMXBean` | > 80% 持续 |

### 线程池层（最容易缺）

| 指标 | 方法 | 告警 |
|---|---|---|
| active | `getActiveCount()` | 持续 == max |
| queue | `getQueue().size()` | > 80% 容量 |
| completed | `getCompletedTaskCount()` | 增长率骤降 |
| rejected | 自定义计数 | > 0 |

### 业务层

- 接口 P99 RT、超时数、错误率；
- 每个下游依赖的 RT / 超时率；
- 异步任务成功率、重试次数。

## 2. 工具速查

| 工具 | 用途 | 常用命令 |
|---|---|---|
| `jps` | 找 Java 进程 | `jps -l` |
| `jstack` | 线程转储 | `jstack -l <pid> > dump.txt` |
| `jcmd` | 全能（首选） | `jcmd <pid> Thread.print`、`GC.heap_info`、`VM.flags` |
| `jstat` | GC 统计 | `jstat -gcutil <pid> 1000` |
| `jmap` | 堆直方图 | `jmap -histo:live <pid> \| head -20` |
| `jinfo` | 查看/修改参数 | `jinfo -flags <pid>` |
| Arthas | 在线诊断 | `thread -n 3`、`dashboard`、`trace` |
| async-profiler | 火焰图 | `profiler.sh -d 30 -f f.html <pid>` |
| `kill -3` | 输出 dump 到日志 | `kill -3 <pid>` |

> 容器里没有 JDK 工具时，可以用本项目的「线程与死锁」「一键诊断」页面等价完成。

## 3. 四类高频故障的排查路径

### 3.1 CPU 打满

```
top -Hp <pid>                     # 找最忙线程（十进制）
printf '%x\n' <tid>               # 转十六进制
jstack <pid> | grep -A 30 nid=0x<hex>
```

| 栈特征 | 根因 |
|---|---|
| 业务方法反复出现 | 死循环 / while 无退出条件 |
| `Pattern` / `Matcher` | 正则灾难性回溯 |
| `JSON.toJSONString` | 大对象序列化 |
| `GC task thread` | 内存压力（查 GC） |
| `C2 CompilerThread` | 启动预热正常，持续高要查热点 |

**代码化**：`ThreadInspector.topCpuThreads()`（`obs-01`）。

### 3.2 内存持续上涨 / OOM

```
jcmd <pid> GC.heap_info           # 各代使用率
jstat -gcutil <pid> 1000          # GC 频率
jmap -histo:live <pid> | head -30 # 实例数最多的类
```

常见根因：无界队列堆积、ThreadLocal 未清理、缓存无上限、大对象。
**注意**：`jmap -histo:live` 会触发 Full GC，生产慎用。

### 3.3 线程池打满

```
1. 看指标：active == max，queue 增长，rejected 上升
2. 看线程栈：线程都卡在同一个下游调用
3. 看下游：RT 是否劣化
4. 处置：超时 + 隔离 + 熔断 + 限流；短期扩容或重启
```

**关键区分**：

- active 满 + queue 满 → 处理不过来（下游慢 / 任务变重）；
- active 低 + queue 涨 → 消费者被阻塞或线程死了；
- active 满 + queue 空 + RT 高 → 单任务本身慢。

### 3.4 死锁 / 卡死不返回

```
jstack <pid> | grep -A 20 "Found one Java-level deadlock"
```

或代码巡检：

```java
long[] ids = ManagementFactory.getThreadMXBean().findDeadlockedThreads();
if (ids != null) { alert(ids); }
```

**注意**：`synchronized` 死锁只能重启；`ReentrantLock` 可中断。
「假死」还可能来自：线程池父子任务同池等待、连接池耗尽、`wait` 没有 notify。

## 4. 怎么读一份 jstack

1. **先看总量与状态分布**：几百个线程里，哪个状态占多数？
2. **按名字分组**：`http-nio-*`、`order-pool-*`、`GC Thread`，先分清阵营；
3. **找同一栈顶**：6 个线程都停在 `HikariPool.getConnection` → 连接池耗尽；
4. **追锁链**：`- waiting to lock <0xaaa>` + 谁 `- locked <0xaaa>`；
5. **找环**：A 等 B、B 等 A，就是死锁；
6. **对比多次 dump**：抓 3 次、间隔 5 秒，卡住的线程栈不变。

本项目 `ThreadDumpAnalyzer` 把 2~5 步自动化了，页面的「jstack 分析」可以直接粘贴。

## 5. 一键诊断的规则

`Diagnostics.diagnose()` 固化了以下判断：

| 检查 | 触发条件 | 级别 |
|---|---|---|
| 死锁 | `findDeadlockedThreads() != null` | ERROR |
| CPU 热点 | 单线程占用采样窗口 ≥ 60% | WARN |
| 线程过多 | > max(200, 核数×32) | WARN |
| 锁竞争 | BLOCKED ≥ 8 且占比 > 20% | WARN |
| 池拒绝 | rejected > 0 | ERROR |
| 队列积压 | > 80% 容量 | WARN |
| 池满负荷 | active == max 且有排队 | WARN |
| 堆压力 | used/max > 85% | WARN |
| GC 压力 | GC 时间占比 > 10% | WARN |

没有异常时返回一条 INFO，避免「诊断了个寂寞」。

## 6. 故障演练（最重要的一节）

> 看过一百篇文章，不如亲手制造一次故障。

页面的「排障演练场」提供 5 种演练，全部是**可控、可停止、daemon 线程**：

| 演练 | 你会看到 | 练习什么 |
|---|---|---|
| CPU 打满 | CPU 曲线飙升、热点线程 100% | 采样定位、火焰图 |
| 构造死锁 | 线程 BLOCKED、死锁告警 | 锁链分析、中断解除 |
| 线程泄漏 | 线程数每秒 +50 | 前缀聚合、创建栈 |
| 堆内存增长 | 堆曲线上升、GC 变频繁 | 堆快照、大对象 |
| 线程池打满 | 队列满、rejected 飙升 | 降级、限流 |

**标准动作**：启动演练 → 等 10 秒 → 一键诊断 → 读 findings → 对照「下一步命令」→ 停止演练。

## 7. 应急手册（照着做）

**接口大面积超时**

1. 看线程池指标：是否打满？队列是否爆炸？
2. 看下游 RT：哪个依赖变慢？
3. 临时：限流 / 熔断 / 降级开关 / 扩容；
4. 保留现场：jstack、GC 日志、火焰图；
5. 事后：定位根因，补超时、隔离、告警。

**CPU 100%**

1. 确认是 Java 进程（不是别的）；
2. `top -Hp` + `jstack` 找热点栈；
3. 若是死循环/正则，先摘流量再重启；
4. 保留 dump，事后修代码。

**内存飙升**

1. `jcmd GC.heap_info`、`jstat -gcutil`；
2. 怀疑无界队列/缓存/ThreadLocal；
3. 紧急：扩容堆或重启，同时摘掉流量；
4. 事后：`jmap` dump + MAT 分析。

**死锁**

1. 确认影响面（哪些接口卡住）；
2. dump 现场（jstack）；
3. 重启恢复（synchronized）或中断线程（ReentrantLock）；
4. 事后：统一加锁顺序 + 死锁巡检告警。
