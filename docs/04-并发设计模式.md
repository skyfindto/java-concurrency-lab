# 04 · 并发设计模式

> 对应用例：`pattern-01` ~ `pattern-09`

并发设计模式不是「炫技」，而是把常见协作问题固化成结构。
认识它们之后，你会在 Spring、Netty、Dubbo、Kafka 客户端里反复看到同样的骨架。

---

## 1. Worker Thread（工作线程）

**意图**：用固定数量的常驻线程反复处理队列里的任务。

```
Producer → [任务队列] → Worker-1 / Worker-2 / ... / Worker-N
```

- 线程复用，避免频繁创建；
- 队列是缓冲，也必须有界；
- 关闭用毒丸（poison pill）或标志位。

**这就是线程池的本质**：`ThreadPoolExecutor` = Worker Thread + 队列策略 + 拒绝策略 + 生命周期。
**坑**：工作线程里抛异常必须 catch，否则 worker 退出、队列没人消费。
**用例**：`pattern-01-worker-thread`

---

## 2. Future / Promise

**意图**：异步调用的「取货凭证」。

```
调用方 --submit--> 执行者（另一线程）
   |                    |
   +---- Future --------+  稍后 get() 取结果
```

- `get()` 的本质就是 `while (!done) wait()`；
- 支持超时、取消、异常传递；
- 演进：Future → CompletableFuture（可编排）→ 响应式。

**坑**：`get` 超时不取消任务；异常被包在 `ExecutionException` 里。
**用例**：`pattern-02-future`

---

## 3. Guarded Suspension（保护性暂停）

**意图**：条件不满足时等待，直到别人唤醒。

```java
synchronized (lock) {
    while (!condition) {
        lock.wait();
    }
    // 条件成立
}
```

- **必须用 while**（虚假唤醒 / 条件被抢走）；
- 必须带超时；
- 现代替代：`Condition`、`BlockingQueue`、`CompletableFuture`。

**坑**：用 `if` 代替 `while`；用 `notify()` 导致漏唤醒。
**用例**：`pattern-03-guarded-suspension`

---

## 4. Balking（止步）

**意图**：条件不满足就**立刻放弃**，而不是等待。

```java
if (initialized) return;          // 快速路径
synchronized (this) {
    if (initialized) return;      // 二次检查
    // 初始化
}
```

- 适合「只做一次」：单例、配置加载、重复请求去重；
- 与 Guarded Suspension 的区别：等 vs 走。

**坑**：只加锁不判断、或判断了不二次检查。
**用例**：`pattern-04-balking`

---

## 5. Thread-Per-Message

**意图**：每个请求一个线程，处理完即销毁。

- 简单、隔离性好、无需队列；
- 平台线程时代不可行（太贵）；
- **虚拟线程让它复活**：百万级并发、同步写法。

**坑**：不限并发会打爆下游；CPU 密集场景仍然要用固定线程池。
**用例**：`pattern-05-thread-per-message`

---

## 6. Two-Phase Termination（两阶段终止）

**意图**：安全地停止一个线程。

```
阶段一：请求停止（flag = false + interrupt）
阶段二：等待善后（finally 清理 + terminated.latch）
```

- 绝不用 `stop()`（会在任意位置抛 ThreadDeath，对象状态不一致）；
- 清理必须幂等（可能被多次 shutdown）；
- 调用方 `awaitTermination(timeout)`，超时记录并告警。

**坑**：只设标志不 interrupt（卡在 sleep 要等超时）；只 interrupt 不设标志（不检查中断的循环停不下来）。
**用例**：`pattern-06-two-phase-termination`

---

## 7. Active Object（主动对象）

**意图**：用「单线程串行处理消息」消除锁。

```
调用方 --方法--> Proxy --消息--> 队列 --> Scheduler（单线程）--执行--> 状态
                    ↑
                返回 Future
```

- 所有状态只被 scheduler 线程访问 → **无需任何锁**；
- Actor 模型、Netty EventLoop、Redis 单线程都源于此；
- 缺点：单线程瓶颈、队列必须有限、调试栈会「跳」。

**坑**：在 scheduler 里做阻塞 IO，整个对象卡死。
**用例**：`pattern-07-active-object`

---

## 8. Half-Sync/Half-Async（半同步/半异步）

**意图**：IO 层只收事件，业务层慢慢处理。

```
[IO/EventLoop 线程] --事件--> [有界队列] --> [业务线程池]
      非阻塞、极快                      阻塞、可扩展
```

- Netty 的 boss/worker、Tomcat 的 Acceptor/Poller/Worker、Redis 6 的 IO 线程；
- **铁律**：EventLoop 里绝不做阻塞操作；
- 队列满时要么阻塞 IO 层（反压），要么拒绝。

**坑**：在 Netty handler 里查数据库 —— 一条 EventLoop 上的所有连接全部卡住。
**用例**：`pattern-08-half-sync-half-async`

---

## 9. Master-Worker

**意图**：主线程分片，工人并行处理，主线程汇总。

```
Master --分片--> Worker-1..N --结果--> Master 汇总
```

- 适合任务独立、数量已知的批处理；
- 与 ForkJoin 的区别：静态分片 vs 递归拆分 + 工作窃取；
- 失败要能定位到「哪个分片」。

**坑**：worker 异常不 catch → 完成计数不归零；共享结果集竞争。
**用例**：`pattern-09-master-worker`

---

## 模式选择速查

| 问题 | 模式 |
|---|---|
| 要限制并发、复用线程 | Worker Thread（线程池） |
| 异步拿结果 | Future / Promise |
| 等某个条件成立 | Guarded Suspension |
| 只做一次 / 重复请求直接返回 | Balking |
| 每请求一线程且 IO 密集 | Thread-Per-Message（虚拟线程） |
| 要安全停止线程 | Two-Phase Termination |
| 状态必须串行访问、又不想加锁 | Active Object |
| IO 与业务要分层 | Half-Sync/Half-Async |
| 大任务分片并行 | Master-Worker |

---

## 在框架里认出它们

| 框架 | 用到的模式 |
|---|---|
| Spring `@Async` / `TaskExecutor` | Worker Thread + Future |
| Netty EventLoop | Half-Sync/Half-Async + Active Object |
| Redis 单线程 | Active Object |
| Kafka Consumer 线程模型 | Worker Thread + 两阶段终止 |
| CompletableFuture | Future / Promise |
| HikariCP | Object Pool + Guarded Suspension |
| Reactor / RxJava | 观察者 + 背压 |
